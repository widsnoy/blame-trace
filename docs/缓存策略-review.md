# 缓存策略复审与实测（2026-10-23）

## 发现与实施

基线为 `9262ba54945942318773118e72ab3716a2888da6`。保留按仓库、HEAD、路径隔离的整文件快照、两个内容版本及 Git 对未保存文本的精确归属判定。

| 发现 | 实施 | 验证依据 |
| --- | --- | --- |
| `exact()` 对两个快照分别计算哈希；同一未命中版本每次读取都会重算，`load()` 还会再计算一次 | 每个条目只保存最近一次版本的指纹；编辑和关闭时清除；同一次读取及同版本后续请求共用 | OI-wiki 两个旧快照下的 1000 次 miss：2000 次哈希降到 1 次；10 个并发 load：30 次降到 1 次 |
| 光标移动即使命中版本也先调用 `document.getText()` | `get()` 接受惰性文本提供函数；扩展只在需要时读取文本，单次 update 内复用 | 回归测试确认版本命中不调用提供函数，连续 miss 只调用一次；未测量 VS Code 的实际文本读取耗时 |
| 失败按内容永久缓存；Git 短暂失败后，同文本不会再尝试整文件构建 | 失败缓存保留 1 秒，之后由下次请求触发重试 | 可控时钟测试验证 999 ms 不重试、1000 ms 恢复；1 秒是节流参数，未经用户输入负载调优 |
| 首个调用者检查 pending，合并的其他调用者却直接拿到原始 Git Promise；失效后可能仍返回旧结果 | 所有调用者共用包含有效性检查和快照发布的 Promise；检查条目身份、pending 身份及取消状态；移除条目时清除 pending | 延迟返回测试覆盖编辑、仓库失效、dispose、LRU 淘汰、不同文本替换；所有等待者均返回 undefined |

版本号必须对应不可变文本；关闭后重开可能复用版本号，因此必须调用 `noteChange()`。扩展已有编辑、关闭事件接线，新增测试覆盖重开后的相同版本、不同内容。

## OI-wiki 性能证据

- 仓库：本机 `../OI-wiki`，HEAD `11d6d53024e624b953754550f0b547823a8ea3ab`。只读取仓库；未修改其文件或配置。仓库原有 `mkdocs-material` 子模块状态为 `?`，测试文件的内容 SHA-256 记录在原始数据内。
- Windows，Node v25.6.1，Git 2.53.0.windows.1。
- 每个文件、每版先预热一次，再交替执行两版各 7 轮，以下为中位数。cold 指新建应用缓存，操作系统文件缓存已预热，不能解释为磁盘冷启动。
- 两版在同一进程中使用各自编译产物；包装 `spawn` 和 `createHash` 记录实际调用次数。断言与计数开销包含在结果中。
- 每个文件、每版的预热轮，将原文首/中/末行以及未保存插入后的首行和对应三行与 `blameLine()` 逐一比较，共 56 次对照，全部通过。

| 文件 | 首次整文件，旧→新（ms） | 同版本 miss ×1000，旧→新（ms） | 撤销+重做，旧→新（ms） |
| --- | ---: | ---: | ---: |
| `docs/lang/index.md` | 85.570 → 85.095 | 2.681 → 0.269 | 0.010 → 0.009 |
| `docs/graph/mdst.md` | 82.429 → 81.292 | 19.616 → 0.346 | 0.044 → 0.027 |
| `docs/math/number-theory/basic.md` | 79.810 → 80.149 | 60.072 → 0.347 | 0.124 → 0.073 |
| `docs/math/number-theory/continued-fraction.md` | 87.839 → 87.070 | 215.539 → 0.372 | 0.436 → 0.222 |

1000 次 miss 是放大重复哈希成本的压力场景：连续查询同一未构建版本，并非连续输入 1000 个不同版本。最大样本每次 miss 的平均摊销成本由约 0.216 ms 降到 0.000372 ms，不能把总差值当成一次光标移动节省的时间。

首次查询和编辑后重建仍各启动 1 个 Git 进程；10 个并发构建请求仍合并为 1 个进程。命中、miss、撤销重做均为 0 个 Git 进程。10000 次已命中版本读取总耗时约 1.9–2.4 ms，两版没有一致的改善趋势；首次及重建也没有明确加速。主要收益是消除重复文本读取、哈希，以及修复失效和恢复行为。

完整样本、每项 min/median/max、进程数、哈希次数见 [原始 JSON](cache-benchmark-2026-10-23.json)。测试不含扩展宿主、UI 渲染、真实连续输入轨迹，也不证明内存峰值降低。

## 复现

新检出环境可从固定提交重建基线，所有产物都在 `out` 内：

```powershell
New-Item -ItemType Directory -Force out/baseline-source | Out-Null

git show 9262ba54945942318773118e72ab3716a2888da6:src/documentCache.ts | Out-File -Encoding utf8 out/baseline-source/documentCache.ts

```

省略基线目录可只测当前实现。旧的 `benchmark-cache.cjs <文件>` 单文件脚本仍可使用。

## 后续优化边界

本次证据不支持扩大缓存或替换 Git 的行映射算法。8 个文档、估算 16 MiB、最多两个快照仍是现行限制。

- 内存预算只估算行数组和输入大小，未精确计算元数据、解析缓冲及在途进程；若要调整，应先测多文档和大文件的峰值堆内存。当前超预算时可能连同新条目一起淘汰，值得在相应负载出现后评估“大条目不入缓存”和优先淘汰 previous。
- 失败接口只返回 undefined，无法区分永久超限与瞬时错误；目前统一重试间隔。若实际出现超限反复重试，应先提供结构化失败原因再分别设置策略。
- 编辑期间仍使用单行查询和 250 ms 空闲重建；应采集真实输入间隔、取消进程数再决定防抖参数，当前数据不足以修改。
- HEAD 不变时，Git 配置、mailmap、浅克隆历史补全等外部输入变化仍缺少专门失效事件；此次没有扩大失效模型。

`npm.cmd test` 共 13 项通过，包括未保存插入/修改/删除、撤销、中文空格路径、SHA-256 仓库及新增缓存生命周期测试。

### 未保存修改的重复性能测量

随后独立启动上述脚本 7 次，每次完整运行 28 个场景，无额外预热；OS 文件缓存并未清空。计时仅包含缓存 get/load，逐行正确性对照和磁盘检查在计时外。原始样本及汇总见 [7 轮性能数据](unsaved-performance-2026-10-23.json)。

最大文件 `continued-fraction.md` 的中位数：

| 操作 | 耗时（ms） | 新增整文件 Git 查询 |
| --- | ---: | ---: |
| 原文首次构建 | 89.23 | 1 |
| 未保存插入 | 90.19 | 1 |
| 未保存替换 | 88.08 | 1 |
| 未保存删除 | 88.30 | 1 |
| 未保存多处修改 | 89.33 | 1 |
| 撤销 | 0.164 | 0 |
| 重做 | 0.180 | 0 |

四个文件各编辑场景的中位数范围为 80.42–90.19 ms，撤销/重做为 0.045–0.180 ms。单次样本存在波动，例如 basic.md 的替换场景最大 158.11 ms，中位数 80.42 ms。7 轮内累计 125,300 行归属对照全部通过。

这些数字不等于键入后标注出现的延迟。扩展的未命中路径有 40 ms 等待；最近 250 ms 内发生过编辑时先查询单行，在单行查询完成后再启动 250 ms 重建定时器，之后执行整文件查询。连续输入会取消过时工作。本轮未测量该调度链的端到端延迟和实际输入负载下的进程数。文本不再变化后，即使一直不保存，也可持续命中当前版本快照。
