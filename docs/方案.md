# Blame Trace：当前行归属与 Squash 溯源方案

状态：第一阶段已按本文实现；第二阶段仍是待验证方案。本文记录设计原理，使用说明见项目根目录 README。

## 目标

在 VS Code 中，把光标所在行最近一次提交的作者、时间和摘要显示在该行末尾。第一阶段只使用本地 Git；后续在普通 blame 指向 GitLab squash commit 时，尝试显示 squash 前的原始提交。

交互范围已确定为**只标注光标所在行**。侧边栏提交列表、整文件逐行标注和状态栏标注不属于第一阶段。

这些产品证明“当前行行尾标注”是成熟的交互模式。本项目的差异点将是 GitLab squash 溯源，而不是复刻完整的 Git 客户端。

## 技术选择

- **语言：TypeScript。** VS Code 支持 TypeScript 或 JavaScript 插件；此项目有普通提交、未提交行、squash 映射成功/失败等多种结果，显式类型有利于保持边界清晰。[VS Code 插件入门](https://code.visualstudio.com/api/get-started/your-first-extension)
- **运行位置：桌面 VS Code 扩展宿主。** 通过 Node.js 启动本地 `git`，以参数数组传参，不拼接 shell 命令。第一阶段不依赖 GitLab 账号或网络；基于本地 Git 的方案暂不覆盖浏览器版 VS Code。
- **行内渲染：`TextEditorDecorationType` 的 `after` 装饰。** 光标变动时清除旧行标注，给新行设置装饰；悬停展示完整信息。装饰文字本身先不承担点击操作，详情入口可放在悬停链接或命令中。[VS Code 编辑器装饰 API](https://code.visualstudio.com/api/references/vscode-api)
- **归属计算：Git CLI 的机器可读输出。** 先用 `git blame --line-porcelain -L <行>,<行> --contents - <headSha> -- <文件>` 查询单行，把编辑器当前文本传给标准输入。`--contents -` 可让未保存的增删行参与计算；新改动的行可能得到“未提交”归属。[Git blame 文档](https://git-scm.com/docs/git-blame)

### 为什么从 Git CLI 开始

`git blame` 已经处理了逐次提交的行归属、文件重命名和未提交文本与历史版本的对齐。插件无需重新实现 Git 的历史遍历。`--line-porcelain` 是面向程序读取的格式，比按人类界面输出拆列稳定。按参数数组启动 `git` 还能正确处理空格与中文路径，并避免文件名被 shell 当成命令。

GitLab 的文件 blame API 也能按 `ref` 和行范围查询，但第一阶段要求查看编辑器内未保存的文本，本地 `--contents -` 更合适；GitLab API 留到第二阶段读取未在本地仓库中的 MR 原始版本。[GitLab 文件 blame API](https://docs.gitlab.com/api/repository_files/#retrieve-file-blame-history)

## 第一阶段：普通 Git blame

### 用户看到什么

光标停在已提交的行时，行末显示类似 `张三 · 3 天前 · 修复登录校验` 的低对比度文字。悬停显示完整 SHA、精确时间、作者和完整摘要，并提供“查看提交”的入口。光标离开该行时，标注随之移动或消失。

未提交的新行或已改动行显示 `未提交`；未跟踪文件、非 Git 文件和无法取得归属的行不显示错误提交。普通 blame 的含义是“当前分支历史中最后修改该行的提交”，不保证它是最初创建该行的提交。

### 数据流

```text
编辑器文件 + 光标行 + 当前文本
        ↓
定位所属 Git 工作树与 HEAD
        ↓
Git blame 单行查询 → 解析 SHA / 作者 / 时间 / 摘要
        ↓
CurrentLineAttribution（committed | uncommitted | unavailable）
        ↓
当前行行尾装饰 + 悬停详情
```

模块边界建议为：`GitRepository` 负责仓库定位和命令执行，`AttributionResolver` 负责把 Git 结果转换为统一的归属对象，`InlinePresenter` 只负责 VS Code 事件和显示。第二阶段可以在 resolver 后增加 GitLab 溯源，而不改编辑器交互。

两层之间的最小契约可以是：

```ts
type Attribution =
  | { kind: 'committed'; sha: string; sourceLine: number; author: string; authorTime: number; summary: string }
  | { kind: 'uncommitted' }
  | { kind: 'unavailable'; reason: string };

type Query = {
  repoRoot: string;
  headSha: string;
  filePath: string;
  line: number;             // Git 的 1-based 行号
  documentVersion: number;  // VS Code 的文档版本
  contents: string;         // 包含未保存编辑的完整文本
};
```

未来的 squash resolver 消费 `committed`，必要时返回带原始提交、squash SHA 和 MR URL 的扩展结果。`unavailable` 不渲染成猜测的作者。

### 一次普通查询如何执行

假设编辑器打开 `src/login.ts`，光标在 VS Code 的第 41 行（从 0 开始），Git 查询行号就是 42（从 1 开始）。执行步骤：

1. 从文件所在目录运行 `git rev-parse --show-toplevel`，定位真实工作树；不能直接使用第一个 VS Code 工作区目录，因为一个工作区可包含多个或嵌套仓库。
2. 在该工作树运行 `git rev-parse HEAD`，取得本次查询的基准提交。分支名只用于展示；归属缓存必须绑定具体 HEAD SHA。空仓库在这一步进入 `unavailable`。
3. 把文件转成工作树相对路径，以参数数组调用 `git blame --line-porcelain -L 42,42 --contents - <headSha> -- src/login.ts`；将 `document.getText()` 经标准输入交给 Git。`--` 把后面的路径与 Git 选项隔开。
4. 解析输出，转换为统一的归属对象。取结果前再次核对活动编辑器、文档版本、光标行和 HEAD；条件变化就丢弃结果。

porcelain 输出的关键字段如下；实际输出还包含邮箱、时区和文件路径：

```text
0123456789abcdef0123456789abcdef01234567 37 42 1
author 张三
author-time 1730000000
summary 修复登录校验
filename src/login.ts
\tif (!token) return;
```

首行依次为对象 ID、**该行在归属提交里的行号**、结果文件行号和可选的连续行数；此例是提交中第 37 行映射到编辑器第 42 行。按字段名解析后续行，未知字段跳过；不要按固定输出行数解析。对象 ID 应接受 SHA-1 的 40 位和 SHA-256 的 64 位。全零对象 ID 表示当前内容没有对应的已提交对象，展示为“未提交”。`author-time` 是 Unix 秒，展示时按本地时区格式化。[Git blame porcelain 格式](https://git-scm.com/docs/git-blame/#_the_porcelain_format)

`--contents -` 可视为让 Git 以编辑器文本作为当前待归属的文件内容，从 HEAD 往前追溯。举例：在原文件第 10 行前插入两行后，编辑器原第 10 行变成第 12 行；查询第 12 行时 Git 仍可能追溯到原提交，新插入的两行则是“未提交”。这解决了直接用编辑器行号查询 HEAD 时的错位。对完全未跟踪的文件，不尝试返回伪造的历史提交。

### VS Code 如何只在当前行渲染

监听 `window.onDidChangeTextEditorSelection` 取得活动光标位置；同时监听活动编辑器切换和文档内容变化。渲染时先对旧编辑器执行 `setDecorations(type, [])`，再对当前行建立 `DecorationOptions`，用 `after.contentText` 将摘要放在行末，用 `hoverMessage` 放完整 SHA、作者及时间。装饰使用主题色、间距和合理的最大文本长度，避免正文横向挤压；空行的锚定位置要在实际 VS Code 中验证。[VS Code Decoration API](https://code.visualstudio.com/api/references/vscode-api)

装饰文字不是普通可点击控件。“查看提交”适合放在悬停中的命令链接，或通过命令面板触发；若使用命令链接，只信任插件自己构造的 URI，并验证传入 SHA。显示和 Git 查询互不依赖：渲染层只接收 `committed`、`uncommitted` 或 `unavailable` 结果。

### 更新与性能

- 光标移动后短暂防抖（初始建议约 150 ms）；文件或编辑器切换时立即清除旧标注。
- 每次查询带上文件 URI、文档版本、行号和 HEAD 标识；返回时若任一项已变化，丢弃结果。
- 先做单行查询和小型缓存，缓存键包含仓库、HEAD、文件、文档版本、行号。保存、编辑、切换分支或仓库时失效。
- `HEAD` 是符号引用时，只监听 `.git/HEAD` 不足以感知同一分支的新提交。每次新查询重新读取 `rev-parse HEAD`，窗口重新获得焦点时也刷新当前行；若需要在光标不动时即时反映外部提交，再监听 `git rev-parse --git-path HEAD` 指向的工作树 Git 元数据及分支引用。不能假设 `.git` 一定是目录（worktree 中它可能是文件）。
- 只有实际测得大文件或频繁移动明显卡顿时，再考虑整文件 `--incremental` blame 与分段缓存；避免一开始为单行需求引入复杂状态。
- Git 执行失败、仓库尚无提交、文件不受追踪时，不在编辑器弹出干扰性错误；提供按需查看的日志以便排查。

实现时使用递增的请求序号：每次光标移动先递增序号，异步查询结束后仅最新序号可渲染。取消正在执行的 Git 子进程可节省资源，但**取消本身不能代替结果校验**，因为进程可能在取消前已经返回。缓存可先设小容量和短存活时间；文档版本改变时，即使未保存，也不能复用旧结果。超大文件要限制传给标准输入的大小及 Git 输出量，并安静降级。

事件处理的核心次序如下，避免旧请求覆盖新行：

```text
selection/document/editor change
  → requestId += 1；清除旧装饰；启动防抖计时器
  → 读取 repoRoot、HEAD、documentVersion、光标行、文本
  → 命中缓存则渲染，否则异步执行 Git
  → 返回时再次核对 requestId + editor URI + version + 行号 + HEAD
  → 仍有效才渲染；否则丢弃
```

若读取 HEAD 与执行 blame 之间正好发生 checkout，必须再核对 HEAD 或改用读取到的 SHA 作为 blame 起点，避免同一次查询混用两个版本。优先采用后者：调用 blame 时传入已解析的 `headSha`，渲染前仍复核仓库当前 HEAD。

### 完成标准

1. 已提交且受追踪的文件，光标移动后只出现一处正确的行末标注；悬停能看到该提交的完整信息。
2. 未保存的插入、删除和修改不会使相邻行错位；当前新改动行显示“未提交”。
3. 快速切换行、文件、分支及多个工作树时，不残留上一次查询的标注。
4. 未跟踪文件、空仓库、无 Git 可执行文件时，插件能安静降级并给出可诊断的信息。
5. 在 SHA-1 和 SHA-256 仓库中正确读取对象 ID；文件路径包含空格或非 ASCII 字符时仍可查询。

## 第二阶段：GitLab squash 溯源

普通 `git blame` 看到的是目标分支里的 squash commit。GitLab MR 数据提供 `squash_commit_sha`，并能列出 MR 的提交；提交关联 MR 的 API 可作为定位入口。因此扩展流程是：blame 得到 squash SHA → 查关联 MR 并核对 `squash_commit_sha` → 取得 MR 原始提交与源分支最终版本 → 将当前行映射到 squash 时对应的行 → 在原始版本上做 blame。[GitLab MR API](https://docs.gitlab.com/api/merge_requests/)、[提交关联 MR API](https://docs.gitlab.com/api/commits/)

### 为什么无法直接“展开 squash SHA”

Git 提交只记录当前提交的树、父提交与元数据。squash commit 在目标分支上是一个新提交，其父链并不指向 MR 中那些被合并的原始提交。因此本地 `git blame` 沿目标分支追溯时只能停在 squash commit；也不能仅凭 squash SHA 在 Git 对象里反推出原始提交列表。MR 与原始提交的关联要从 GitLab 元数据或仍保留的源分支取得。[GitLab squash merge 说明](https://docs.gitlab.com/user/project/merge_requests/methods/)

### 第二阶段的逐行解析算法

以下算法是待真实 GitLab MR 验证的设计，不把“相同文本”直接当成同一行：

1. **锁定 squash 版本。** 普通 blame 若返回 squash SHA `S`，保存 porcelain 首行的原始行号 `nS`。这表示当前行在提交 `S` 的该文件里对应第 `nS` 行；后续提交带来的文件行号变化已由普通 blame 处理。若普通 blame 返回的不是 `S`，保持普通结果，不触发 squash 溯源。
2. **找到 MR。** 用 GitLab 的“提交关联 MR”接口查候选项，只接受 `squash_commit_sha === S` 的已合并 MR。查询不到、多个候选无法唯一确定或无访问权限，都保持普通结果。
3. **锁定原始版本。** 读取 MR 提交列表及合并时的源分支 head `H`。可结合 MR diff version 的 `head_commit_sha`、`base_commit_sha` 和 `start_commit_sha` 判断版本；不能用当前同名分支的 HEAD 代替，因为分支可能已经删除、移动或重建。[GitLab MR diff versions](https://docs.gitlab.com/api/merge_requests/#retrieve-merge-request-diff-versions)
4. **映射文件与行。** 读取 `S` 和 `H` 各自的文件内容，处理文件改名后比较两侧内容。内容完全相同则 `nH = nS`；不同则通过 diff 的未改动区块建立 `S` 行号到 `H` 行号的映射。若 `nS` 落在冲突解决或其他改写区块，或重复文本导致对应关系不唯一，则结果为“不确定”。
5. **查原始提交。** 对 `H` 的对应文件第 `nH` 行执行 blame，得到原始 SHA `O`。本地有对象时用本地 Git；否则可请求 GitLab 按 `ref=H` 的文件 blame API。再核对 `O` 是否属于该 MR 的提交集合；若归属到 MR 之前的基线提交，不宣称它是 squash 内的原始提交。
6. **展示来源。** 只有文件/行映射与提交集合核对都通过，才显示 `原始提交 O · 作者 · 摘要`，悬停同时保留 squash SHA `S` 和 MR 链接；其余情况显示普通 `S` 的 blame，并解释未能确定的原因。

这一映射**不能只按行号直接对应**：目标分支同期变动、冲突解决、重命名和后续编辑都可能改变行号或内容。初期只在文件内容能可靠对应时显示“原始提交”；否则保留普通 squash blame，并标明“无法确定 squash 内的具体提交”。原始提交或文件对象也可能因仓库清理而不可用。[GitLab 仓库清理说明](https://docs.gitlab.com/user/project/repository/repository_size/)

第二阶段再确定 GitLab.com / 自建 GitLab 地址、认证方式、跨项目 MR、API 分页和请求缓存。第一阶段的数据模型预留 `source: local-git | gitlab-squash` 与 `mapping: verified | ambiguous | unavailable`，但不提前接入网络。缓存分别以 `(项目, squash SHA)` 保存 MR 关联、以 `(项目, 源 head SHA, 文件路径, 行号)` 保存原始 blame；不要把网络请求绑在每一次光标移动上。

## 实施顺序

1. 建立 TypeScript VS Code 插件骨架和当前行行尾装饰。
2. 接入本地 Git 单行 blame，完成未保存内容与工作树切换处理。
3. 做悬停详情、开关和必要配置；用不同仓库状态验收第一阶段。
4. 用真实 GitLab squash MR 验证可获取的数据与行映射，再细化第二阶段实现。
