# Blame 文档缓存设计草案

2026-10-23 复审与后续实现见 [缓存策略-review.md](缓存策略-review.md)，包含重复哈希消除、惰性读取、失败重试、并发失效修复和 OI-wiki 的 7 轮对照数据。下文为早期设计与第一版记录，现行行为以复审文档和代码为准。

状态：第一版已在 `feat/document-blame-cache` 实现。目标是让编辑后的缓存失效范围更小，并避免在同一文件中逐行重复执行 blame。下文保留设计推导；实际落地范围见文末。

## 改造前行为与问题

当前插件用 `(仓库根目录, HEAD, 文件路径, document.version, 行号)` 缓存单行归属，最多保存 100 条，按写入顺序淘汰。活动文档一有编辑就清空所有文件的缓存；任何文档保存或关闭、窗口重新获得焦点也会清空全部缓存。缓存命中很快，但编辑一个字符后，其他文件以及该文件未受影响的行都要重新查询。单行查询仍通过 `git blame -L n,n --contents -` 使用编辑器中的未保存文本。

这里要分开处理两件事：**缓存归属数据**与**把当前文档行映射到已缓存的行**。仅按行号沿用旧结果是不安全的：在文件开头插入一行会移动后面所有行号；重复文本、剪切粘贴、多光标编辑也可能让映射产生歧义。

## 参考实现

| --- | --- | --- |

### OI-wiki 的成本对照

在 OI-wiki 上，对每个文件预热后各测 5 次，取中位数；单行查询取文件中间行，整文件使用 `--incremental --contents -`。这是 Git 命令耗时，不含 VS Code 渲染和解析输出：

| 文件 | 行数 | 单行 | 整文件 | 整文件输出 |
| --- | ---: | ---: | ---: | ---: |
| `docs/lang/index.md` | 8 | 86 ms | 86 ms | 1.3 KB |
| `docs/graph/mdst.md` | 238 | 74 ms | 83 ms | 17.7 KB |
| `docs/math/number-theory/basic.md` | 536 | 53 ms | 81 ms | 45 KB |
| `docs/math/number-theory/continued-fraction.md` | 1778 | 54 ms | 87 ms | 247 KB |

在这些样本中，整文件查询比单行贵 0–33 ms，但随后换行无需再次启动 Git。不能由此推断所有仓库都适合整文件查询：历史深度、行数和输出大小会改变成本。

## 建议的数据模型

```ts
type DocumentSnapshot = {
  repoRoot: string;
  head: string;
  uri: string;
  version: number;
  contentHash: string;
  lineCount: number;
  rows: readonly Attribution[]; // 与该版本文档行号一一对应
  outputBytes: number;
};

type DocumentEntry = {
  exact?: DocumentSnapshot;      // 当前版本可直接展示的结果
  previous?: DocumentSnapshot;   // 编辑前的不可变快照，供撤销和映射分析
  pending?: Promise<DocumentSnapshot | undefined>;
  generation: number;            // 防止旧异步结果覆盖新版本
};
```

以 `(repoRoot, HEAD, document.uri)` 定位文档项，`version` 和 `contentHash` 判断快照是否与当前文本完全一致。读取同一版本的任意行是数组索引操作。提交摘要等元数据可按 SHA 共享，避免每行复制字符串。

初版建议仅保留打开过的最近 8 个文档，总缓存预算 16 MiB；单个文档沿用现有 8 MiB 输入上限，整文件输出先限制为 2 MiB。这些是待实测的容量参数，不应作为文件正确性的判断。超限时退回现有单行查询。淘汰按最近使用时间，关闭文档只移除该文档的活动状态，有限容量内的不可变快照可继续保留以支持快速重开。

## 查询与编辑流程

1. **首次查询**：若没有当前文档的精确快照，执行一次 `git blame --incremental --encoding=UTF-8 --contents - <HEAD> -- <path>`。解析器按结果行号和区间填充数组，处理乱序区间、重复 SHA 元数据和全零 SHA。相同 `(HEAD, URI, version)` 的并发请求共享一个 Promise。
2. **缓存命中**：确认文档版本、HEAD 和请求序号后，直接读取 `rows[line]`。相对时间在显示时重新计算，不存成固定文字。
3. **文档编辑**：只处理发生编辑的文档。把 `exact` 保留为 `previous`，记录编辑范围和行数变化，取消旧版本的后台计算；新版本暂时没有整文件精确快照。不要仅凭旧行号或相同的行文本显示旧作者。
4. **编辑期间的当前行**：若没有新版本快照，沿用现有单行 `--contents -` 查询，得到准确结果；对同一版本、同一行的并发查询去重。用户连续输入时取消过时请求。
5. **编辑停止后**：在短暂空闲后异步重建一次整文件快照。新的编辑会取消或废弃旧任务；只有 HEAD、URI、版本和 generation 均匹配时才发布结果。这样一次重建可服务该版本之后的所有光标移动，自动保存不会单独触发重建。
6. **撤销或重做**：若当前文本的哈希与保留的旧快照一致，且 HEAD 与路径相同，可直接恢复该精确快照；否则按新版本处理。

编辑范围可以用于维护旧行到新行的**候选映射**：编辑区前的行保留位置，区后的行按行数差平移，编辑区及边界行标记为待验证。候选映射可用于预取和定位脏区，但第一阶段不直接据此显示提交作者。原因是 Git 对 `--contents -` 的 diff 对齐可能在重复行和移动代码时改变归属，文本相同不足以证明结果相同。若以后要显示候选结果，必须先用对照测试界定可复用的编辑类型，并对歧义回退到 Git 查询。

## 失效规则

| 事件 | 处理 |
| --- | --- |
| 光标在同一文档移动 | 复用该版本快照；不清空缓存。 |
| 当前文档编辑 | 只让该文档的精确快照过期；保留旧快照，按上面的流程重建。 |
| 保存但文档文本不变 | 不清除归属。查询始终使用 `--contents -`；HEAD 和文本未变时，保存本身不改变输入。 |
| 其他文档保存或关闭 | 不影响当前文档；关闭时处理对应文档项。 |
| 仓库 HEAD 改变 | 仅让该仓库旧 HEAD 的活动快照失效；新查询使用新 HEAD。 |
| 文件路径改变、仓库切换 | 使用新的键；旧项按容量淘汰。 |
| 窗口重新获得焦点 | 核对 HEAD 和活动文档版本，不因聚焦事件本身清空所有快照。 |
| Git 查询失败、文件超限 | 不缓存失败结果；使用单行查询或保持无标注。 |

## 准确性与验证

整文件快照必须与当前单行命令一致：对固定 `HEAD` 和完全相同的文档文本，逐行比较 `--incremental --contents -` 解析结果与 `--line-porcelain -L n,n --contents -`。覆盖新增、删除、同一行修改、文件开头插入、多光标编辑、撤销重做、重复行、重命名、暂存后再编辑、SHA-256 仓库和提交/切换分支期间的并发请求。

性能验收在 OI-wiki 上记录首次标注延迟、同文件连续查看 10 行的 Git 进程数、连续输入时的进程数、快照内存占用和超限回退比例。若整文件解析使首次显示明显慢于现状，可先用单行结果显示当前行，同时在后台建立整文件快照。

**实现顺序**：先加入精确版本的整文件快照与单文档失效；再做编辑后空闲重建和撤销复用；最后评估候选行映射是否值得承担额外复杂度。第一阶段不改变现有归属语义。

## 第一版实现记录

- `src/git.ts` 用 `git blame --incremental --contents -` 获取整文件结果；解析器按结果行号回填乱序区间，支持重复提交元数据与 SHA-256。整文件输入仍限 8 MiB，输出限 2 MiB；失败或越限时回退到精确的单行查询。
- `src/documentCache.ts` 以仓库、HEAD、文件路径定位条目，同版本直接读取数组。版本改变时只在需要复用旧快照时计算内容哈希；保留当前与上一份快照，支持最近一次编辑的撤销复用。缓存按最近使用淘汰，最多 8 个文档，估算容量 16 MiB。相同内容的并发整文件请求共享一次 Git 查询。
- 文档内容变化只取消该文件的待完成查询并使该文件快照过期；旧快照仍可在内容完全一致时复用。编辑期间的当前行继续用单行 Git 查询，停止输入 250 ms 后异步重建整文件快照。保存事件不失效缓存；关闭文档只清除活动计时器并要求下次打开时重新核对文本；HEAD 改变仅清理该仓库的条目。
- 尚未实现旧行到新行的候选映射，也未在编辑期间直接展示未经 Git 核对的旧归属。撤销复用最多覆盖当前和上一份快照。

在 OI-wiki 的 `docs/math/number-theory/continued-fraction.md`（1777 个有内容的行）上，单次测量首次整文件查询约 91 ms，随后查询 10 行的缓存读取合计约 0.06 ms；同样 10 行逐行查询合计约 599 ms。这里是命令行 Git 与 Node 缓存成本，不包含 VS Code 的 UI 渲染；可用 `node scripts/benchmark-cache.cjs <文件路径>` 复测。
